Making sense of an agent’s activity

Operators need to know what an agent did, why it happened, and whether they need to act. I used those questions to structure the monitoring interface.

What happened? Why? Do I need to act?

The monitoring interface surfaced signals, triggers, actions, timestamps, and confidence scores. The information was there. Finding the story inside it took too much work.

I led the redesign of the information architecture and UI language. I mapped the relationship between signals, triggers, and actions, then aligned labels across UI, documentation, and engineering specifications. The design moved from an event overview into details and supporting evidence.

Give each question a place in the interface

User questionContent pattern
What happened?An event summary and status. Name the event in language the operator recognizes.
Why did it happen?Explain the condition or threshold that triggered it. Make supporting evidence available in the event detail.
How serious is it?Pair a severity label with a description of the impact or urgency.
What did the system do?Name the action. Distinguish automated action, recommendation, and required human review.
What should I do next?Link to the next workflow when there’s a specific action to take.

The result was a set of event, status, and explanation patterns the team could reuse as more agent types were added.

Make evidence available at the right depth

Lead with the event, then give operators a route to the cause and supporting evidence before they act.
