Capability · Developer experience (DX)

Designing the path from API discovery to successful integration

Developer experience is more than writing an API reference. It is making the journey from “Can this solve my problem?” to “I have a working, supportable integration” clear, verifiable, and maintainable.

What developer experience means in my work

I combine technical writing, information architecture, content design, and editorial governance to help developers understand a platform, choose an integration path, complete a task, and recover when something fails. The documentation is part of the product interface: it exposes requirements, behavior, dependencies, and supported decisions.

At Marqeta, I led developer content strategy for a unified payments API, mapped services and developer journeys, audited migration gaps, developed terminology, and peer-reviewed documentation. At IBM, I documented enterprise AI software workflows across installation, upgrades, model evaluation, known issues, and troubleshooting, validating technical behavior with engineering partners.

Those are professional case studies. The Cohere editorial portfolio is a separate, independent, public-source exercise that demonstrates how I would connect developer education with editorial strategy.

The developer journey I design for

Instead of treating every documentation page as an isolated deliverable, I map the decisions and evidence that connect them.

A good journey connects these surfaces without duplicating the reference in every guide. It also gives each page a clear maintenance owner and a trigger for review when the product changes.

How I audit developer content

  1. Reconstruct the task: Define who is integrating, their starting state, dependencies, expected result, and likely failure points.
  2. Check the source of truth: Compare the guide against API or SDK documentation, product specifications, release information, and engineer-reviewed behavior.
  3. Walk the happy path and recovery path: Confirm that a developer can identify the setup, perform or reproduce the steps, recognize success, and respond to failure. Mark untested examples rather than presenting them as verified.
  4. Check the handoffs: Follow links from launch to quickstart, task guide, API reference, troubleshooting, and migration details. Resolve conflicting terms.
  5. Separate content gaps from product gaps: A missing explanation may require a rewrite; a blocked request may require engineering or access changes.
  6. Record decisions and revalidation triggers: Track affected pages, the reviewer, evidence source, change event, and unresolved risk.

How developer experience strengthens my Cohere editorial strategy

For a product announcement, I ask what a developer must be able to evaluate after reading it. I would connect the launch narrative to a working example, a fair comparison, authoritative API reference, and fallback or limitation guidance. That makes developer education a complement to product storytelling rather than an unrelated documentation stream.

My independent Rerank comparison guide explores the reader’s decision. The simulated commissioning exercise shows when a guide might be more useful than another announcement. These are editorial artifacts, not a claim that I ran Cohere integrations, tested their SDKs, or measured adoption inside Cohere.

For a production-ready developer sample I would add a separately versioned, technically verified example with explicit credentials, a request and expected response, error behavior, and a documented validation environment. I would seek Engineering or DevRel review before presenting the sample as tested.

How I would measure developer content quality

Useful measures go beyond page views. I would define a reader task and a denominator before claiming a result.

  • Time to first successful request: Time from beginning setup to a verified API response, measured with representative developers and controlled prerequisites.
  • Evaluation completion: Eligible developers who finish the intended comparison divided by those who started, with documented event definitions.
  • Error recovery: Whether someone can diagnose and resolve a representative failure using the guide, without undocumented assistance.
  • Migration task success: Whether developers identify changes, verify compatibility, and complete a rehearsal before deploying.
  • Documentation reliability: Broken links, stale references, example-test failures, and age of unresolved doc issues, with severity and owner.

These are proposed methods. No quantitative outcomes are attributed to my employer projects or to Cohere without supporting evidence.
