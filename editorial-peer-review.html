Editing an API migration guide

The draft announces a better API. The reader needs to decide whether their integration is ready to move. Here’s how I’d work with the writer to close that gap.

Task topicCoach a writer through a technical revision and verify the claims.

What this exercise shows

An API is a way for two software systems to communicate. When a payments provider changes its API, customer teams need to know what to update and how to test it. This fictional example shows the coaching and technical editing approach I’d bring to a Cohere developer guide.

Steps at a glance

  1. Identify what the reader needs to decide before changing their integration.
  2. Give the writer a structural revision and one model passage.
  3. Agree on the next draft and the facts that need review.

A fictional launch, draft, and review, inspired by my API migration and peer-review work at Marqeta and my release documentation at IBM.

The assignment

A writer is preparing a migration guide for a fictional payments API. The audience already has a live integration and needs to estimate the work, test it, and decide when to switch. Product Marketing wants to explain why the API is changing. Engineering needs readers to account for a different event schema.

For this exercise, the product brief says the new API has a test environment and uses a different status and event schema. Existing customers need to update how they read those fields. The brief gives us no confirmed retirement date, performance data, or instructions for reversing a switch.

My first note to the writer

Keep the idea of one place to start. It’s a good promise for this guide. Give it to the reader as a checklist: what changes in their integration, how they can check it, and what still needs a decision before they switch. The release rationale can follow. On your next pass, try writing the headings as questions a developer would ask at each step. Let’s review those together before we polish the sentences.

I’d ask the writer to revise the rest of the draft using the sample below. In the next review, we’d read the headings by themselves, then walk a developer through the guide and watch where they have to ask for more information.

Before and after

Simulated first draft

Our new unified API makes payments faster and easier. Migration is seamless: update your endpoint, test your integration, and go live when you’re ready. The new status experience makes it simple to track payments.

Sample revision for the writer

Before you switch to the unified payments API, check how your integration reads payment statuses and events. The new API sends these in a different format. If your code uses them to update a payment record, review those mappings first.

In the test environment, send a payment request and follow it through each outcome your integration handles. Compare the API response and any events with the status your application shows. Resolve discrepancies before scheduling the switch.

I moved the event-schema change ahead of the setup steps because it affects the effort to migrate. I replaced the promise of a smooth migration with a test a developer can use. Benefits go back in when we can explain what changed and support the claim.

Decisions before publication

DecisionEvidence and reviewer
Publish the changed status and event guidanceEngineering checks the mappings and walks through the test cases with DevRel. Add links to the versioned API reference.
Hold speed and retirement claimsProduct Marketing supplies a comparable benchmark for any performance claim. Product and the appropriate reviewers confirm lifecycle dates and wording before publication.
Keep rollout guidance out of the sample revisionEngineering confirms supported rollout and recovery options. The writer links to the verified procedure once it exists.

Hand it back with a definition of done

A developer can identify which code to inspect, demonstrate that the test flow handles the outcomes they depend on, and find the authoritative rollout guidance. The writer owns the next draft. I’d review the revised opening, verify the claims against the approved sources, then check that the release note and guide use the same terms.
