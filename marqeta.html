Case study · Marqeta

Making a unified API easier to adopt

How I structured documentation around the work developers do when they adopt a unified API for commercial payments, banking, and money movement.

Where does integration actually begin?

For a team starting from scratch, the first question might be which services it needs. A team moving from a legacy API has a different question. Which parts of our integration have to change, and what can we keep?

I led the developer content strategy for this part of the platform. I mapped systems, services, and developer journeys, and audited existing integrations to find where migration guidance was needed. I worked with Marketing on product content, developed glossaries, and peer-reviewed other writers’ drafts.

Design around the next decision

I used the journey to decide what documentation to put together and where the reader needed a link out. A migration guide can start with what changes. An API reference can carry field-level details. The integration guide can explain the order in which the pieces come together.

Illustrative audit questions

Can a developer make the move from here?

  • Can they locate the replacement guidance for a legacy workflow?
  • Can they tell what they need to change, verify, or leave as is?
  • Do the guide, reference, and glossary use the same terms?

What the migration audit changed about the plan

I started with existing customer integrations and mapped the tasks a developer would need to revisit. That gave me a way to organize the migration guidance by what customers had to change, verify, or carry over. It also let me separate decisions that belong in a migration guide from details that belong in the API reference.

I built reusable content-audit skills to help surface gaps in developer guidance. I use an audit to find candidates for review, then check each gap against the workflow and product source before deciding what to rewrite.

Help writers make the same call across surfaces

I developed product glossaries, worked with Marketing on product language, and reviewed other writers’ drafts. Across those surfaces, I look for the same thing: can readers tell when two terms refer to the same capability and when the distinction affects their integration?
