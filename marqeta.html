Case study · Marqeta

Making a unified API easier to adopt

I organized the unified payments API guidance around integration decisions, including what developers need to test before migrating.

From product architecture to a developer adoption journey

The problem: A unified payments API can simplify a platform’s service model while creating a new learning task for developers. A new integrator needs to identify capabilities and prerequisites. An existing integrator needs to understand which legacy behaviors, dependencies, and implementation decisions change.

My responsibility: As Senior Information Developer, I led developer content strategy for this area of Marqeta’s commercial payments, banking, and money movement platform. I mapped systems and services, organized developer journeys, audited documentation gaps for legacy customers, developed shared product terminology, collaborated with Marketing, and peer-reviewed technical content.

The strategic question: How do we make it easier for developers to choose an integration path, understand what changes, and find the authoritative details needed to validate their implementation?

This case describes my professional work at the level I can share publicly. The journey and decision tables below are simplified reconstructions, not customer-specific architecture diagrams or performance findings. No confidential code, specifications, or customer data are reproduced.

1. Diagnose the documentation problem

I began with the work a developer must complete, rather than the product’s internal organization. A greenfield implementation and a migration have different starting points, dependencies, and definitions of success. I mapped the services involved and used existing integration patterns to identify where documentation had to guide readers through a change.

Audit questions I used to guide the work

  • Can a developer identify the service or combination of services that fits the intended payment workflow?
  • Which prerequisites and dependencies must be resolved before a test or migration?
  • What must an existing integrator change, verify, or retain?
  • Where should readers find implementation steps, field-level details, and troubleshooting information?
  • Are the same concepts named consistently in product messaging, guides, and reference content?

The audit distinguished missing or unclear guidance from questions that needed confirmation against the underlying workflow or product source. I developed reusable content-audit skills to surface possible gaps, then used editorial review rather than treating automated findings as authoritative.

2. Design the journey around developer decisions

The goal was a connected information architecture. The migration guide would lead with developer-facing differences; an integration guide would explain the sequence of work; and the API reference would remain the source for detailed fields and operations. This reduces duplication and gives each topic a clear job.

3. Turn the migration audit into content priorities

I reviewed existing customer integration paths against the unified service model. That let me organize guidance around the tasks developers would revisit rather than writing one undifferentiated description of the new API.

4. Carry editorial consistency across teams

The content strategy extended beyond individual documentation pages. I collaborated with Marketing on product language, developed product glossaries, and peer-reviewed fellow writers’ drafts. That helped connect how a capability is introduced to how a developer is expected to implement it.

Editorial decisions: Keep product names stable, distinguish similar concepts when the difference matters to an integration, link claims to current technical sources, and make migration requirements visible where developers will look for them.

Technical verification: A publishable guide needs product and engineering confirmation for behavior, prerequisites, schema, and version-specific details. The exact review and sign-off path is not documented in this public case study, so I do not present a fictional approval chain as an established Marqeta process.

5. What the work produced, and how I would demonstrate impact

Documented contributions: The work produced an integration-focused content structure, a task-based approach to migration guidance, reusable gap-audit skills, shared terminology, and cross-functional editorial review. These are outputs of the work described here, not independently measured adoption results.

Evidence I would use to validate effectiveness: With approved access to actual data, I would measure whether developers can locate the migration path, accurately identify required changes, complete a test integration, and resolve common errors. I would compare task completion and support friction with a suitable baseline, segmenting new adopters from migrating customers and checking for product or access changes that could explain the difference.

The contribution

I turned a complex API service model into a clearer set of developer decisions, connecting integration and migration guidance, reference content, terminology, and editorial review.
